Build the system from real screens.

A practical plan to refactor the current interface into a documented component system. Atomic design supplies the vocabulary. Storybook supplies the workshop, tests, and review surface.

The proposal in one sentence

Use atomic tiers for reusable presentation, keep connected product behavior inside features, and migrate one complete journey at a time.

No big-bang rewrite. The current product stays usable while each migrated component gains stories, states, tests, and a clear owner.
01 · Current system

The UI is already a system. It is hidden in flat folders.

The repository has useful primitives and semantics, but page code, connected behavior, and reusable presentation often live side by side. The largest risk is not missing components. It is extracting the wrong boundaries.

02 · Recommendation

Adopt a hybrid atomic architecture.

Pure atomic folders become vague once domain behavior appears. The proposed model keeps atomic design where it is strongest, then adds a parallel feature layer for booking, messaging, identity, safety, discovery, and account behavior.

Recommended direction

Atomic for form. Features for behavior.

Atoms through templates describe reusable UI composition. Features own domain decisions, provider access, mutations, and routing. Pages connect those two worlds and should stay thin.

Share contracts before code

Align token names, component names, intents, and states across web and mobile. Promote implementations only after two real consumers prove they are compatible.

Migrate a complete journey

Start with booking because it exercises social actions, status, money, dates, empty states, editing, and responsive layout. It will test the system better than an isolated button catalog.

Keep routes boring

A route should resolve access and data, select a page composition, and supply handlers. It should not define a new button, card, status treatment, or layout rule.

03 · Atomic model

Classify by responsibility, not size.

Click each level to inspect its boundary. The deciding questions are what the component knows, which dependencies it imports, and whether it remains useful outside one feature.

Tier 00 · Shared vocabulary

Foundations define every legal visual decision.

Color roles, spacing, typography, radii, shadows, breakpoints, motion, and icon rules live here. Foundations are values and guidance, not rendered components.

05 · Story standard

A story is a state contract, not a gallery tile.

Every reusable component should document the states that matter to a member, Companion, or admin. Stories should render deterministically without a live account, backend, clock, or network.

S1

Core variants

Default, semantic intent, size, density, selected state, and supported composition.

Default · Self · Social · Danger
S2

Interaction

Use play functions for keyboard use, menus, forms, toggles, dialogs, and callback assertions.

Opens · Submits · Rejects
S3

Data states

Represent loading, empty, partial, error, success, offline, and recovery when the component owns those states.

Loading · Empty · Error · Retry
S4

Content pressure

Use long names, long Strengths, missing images, zero values, large amounts, and realistic booking notes.

LongContent · MissingMedia
S5

Environment

Render light and dark themes plus narrow, standard, and wide viewports. Test both user roles when permissions affect presentation.

Dark · Narrow · CompanionView
S6

Quality gates

Every story is a render check. Add accessibility failure gates for new work, interactions for behavior, and visual snapshots for stable patterns.

06 · Migration plan

Refactor in slices that can ship independently.

Each phase has a stop condition. A phase is complete when the migrated code is in use, its stories and tests pass, and no duplicate implementation remains in that slice.

Phase 0

Interface inventory and rules

Capture distinct controls, cards, forms, navigation, shells, and states across web, admin, and mobile. Record duplicates and intentional exceptions. Agree on naming and dependency rules.

Exit checkEvery current UI pattern has an owner, proposed tier, and keep, merge, split, or retire decision.
Phase 1

Storybook spine and foundations

Add the React Vite Storybook, import the real global tokens, provide light and dark modes, define viewports, add provider mocks, and document semantic accents.

Exit checkA static Storybook build succeeds. New stories can run render and accessibility checks in the existing Vitest workflow.
Phase 2

Booking vertical slice

Extract Button, StatusPill, booking fields, BookingRequestCard, editor, and WorkspaceShell boundaries. Split presentation from mutation logic. Migrate the booking surfaces in app.tsx and messages.tsx.

Exit checkMember and Companion booking states render in Storybook and in the app with focused tests for decisions, editing, errors, and long content.
Phase 3

Page and feature extraction

Repeat the slice for messaging, discovery, account, identity, safety, and social. Extract only proven patterns. Keep provider calls and domain rules in their owning features.

Exit checkRoute files mostly compose page components and connect data. The web stylesheet no longer owns migrated component rules.
Phase 4

Admin and mobile catalogs

Add admin stories to the web catalog. Create a separate React Native Web Storybook for mobile primitives and compositions. Align semantic contracts without forcing renderer sharing.

Exit checkAdmin and mobile components have the same documentation standard. Native-only gaps are listed and manually verified.
Phase 5

Enforcement and cleanup

Add import-boundary checks, a story requirement for reusable components, static Storybook builds in CI, and a retirement pass for dead CSS and duplicate components.

Exit checkThe repository gates, Storybook build, component tests, and agreed visual checks pass from a clean checkout.
1

No bulk file move before the interface inventory and naming agreement.

2

No shared package until two consumers prove matching props, behavior, and styling needs.

3

No connected backend or auth client inside atoms, molecules, organisms, or templates.

4

No page migration without stories for important empty, loading, error, and permission states.

5

No removal of old code until the new component is used by the real route and focused tests pass.

6

No change to the black-and-white theme or the established self, social, admin, and danger meanings.

07 · Confirmation

Five decisions unlock implementation.

The recommended choices are selected. Toggle any item that needs revision, then copy the summary into your reply. Approval of this proposal would authorize planning the refactor. It would not authorize dependency installation, code migration, publication, or deployment.

Use the hybrid architecture

Atomic tiers own reusable presentation. Feature folders own connected product behavior.

Start with one React DOM Storybook

Web and admin share one catalog. Mobile gets a renderer-specific catalog in a later phase.

Use booking as the first slice

Booking tests the component boundaries with social actions, roles, status, money, forms, and errors.

Share semantics before implementations

Web and mobile align names, tokens, intents, and state contracts. Code moves to packages only after proven reuse.

Migrate incrementally

Each journey moves only after focused stories and tests exist. There is no all-at-once rewrite.

All five recommended decisions are selected.
