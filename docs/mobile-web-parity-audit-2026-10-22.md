# Mobile and web parity audit

Date: 2026-10-22. Base: `8c3da25` (Oct 11 parity) through `1fc2e08` (Oct 21).

Scope: `apps/mobile` (Expo native) against `apps/web` web client and shared Convex backend. Evidence includes source inspection, automated tests, and isolated Storybook browser inspection at a 320-pixel viewport. No installed-device, live-provider, cloud-build, or deployment verification was performed. Unrelated dirty web files (`apps/web/src/styles.css`, `apps/web/src/features/social/SocialCompositions.stories.tsx`, `apps/web/tests/unit/reviewMediaStyles.test.ts`, `apps/web/tests/unit/tooltipPattern.test.ts`) and untracked artifacts (`artifacts/`, `tmp-shot.mjs`) were left untouched.

Prior audits: `docs/mobile-web-parity-audit-2026-10-11.md` and `docs/mobile-web-parity-implementation-2026-10-11.md`. The Oct 11 implementation closed Circle approval, media, polls, moderation recovery, replies, notification targets, profile content, pagination, guidance, images, appearance, calendar, video, and share-link gaps. This audit covers only what changed on web since then. The three-week commit inventory and the six follow-up adaptations are in `docs/mobile-three-week-feature-audit-2026-10-22.md`.

## Native boundaries (intentional differences)

- Identity verification capture and retention terms stay on the website handoff. Mobile must preserve return navigation and session continuity; no native ID capture is proposed.
- Post composer stays inline and expanding on small screens instead of the web dialog; the live-card preview is a web layout, not a missing capability.
- Video stays in `NativeVideoViewer.tsx` with explicit failure and retry states instead of the embedded web player.
- Role-specific booking detail routes (`/booking/[id]`, `/companion-booking/[id]`) stay instead of forcing both roles into one workspace, provided both render completion, evidence, and messaging.
- External link normalization stays allowlisted (`shareLinks.ts`, `webLinkRoutes.ts`); universal-link association and installed-app delivery remain unverified.

## Final disposition of the baseline gaps

| Area | Final mobile disposition |

| Weekly availability and booking slots | Closed. Public mapping preserves the backend distinction between legacy `undefined` and explicitly closed `[]`. Edit opens the selected month and day. Month navigation cannot enter past months or leave 2000 through 2100. |

## What was implemented (final evidence)

All changes are mobile-only. No Convex functions, web routes, styles, or shared packages were edited. This supersedes the first-pass notes: every item below was re-verified against the working tree.

1. Scheduling and availability.
   - `data/companionAvailability.ts`: schedule normalize/summarize, `availabilityGate` (legacy `undefined` defers to the server with free input; configured `[]` and outside-window starts block submit with product copy), `formatMinutes` (1440 renders as 12:00 AM midnight), Manila formatting plus month helpers.
   - `WeeklyAvailabilityEditor.tsx` (presentation + connected): weekday pickers, add/remove windows, 15-minute steppers, shared-validation errors, save through `companions.updateAvailability` with success/error copy. Wired into Companion tools for existing profiles.
   - `BookingSlotPicker.tsx` (connected + presentation): owns the `bookings.availableSlots` month query, duration-dependent Manila dates/times, busy-conflict exclusion from the server, stale-selection clearing on Companion/duration/month/data change, loading/unconfigured/empty states, selected-month restoration, and bounded navigation. `companions.bookingAvailability` is a submit gate, not only a notice. Configured schedules validate the selected live slot and do not parse obsolete free-form inputs; legacy schedules keep free input.
   - Companion profiles render `CompanionAvailabilitySection` from `getPublic`'s `weeklyAvailability`.
2. Booking evidence. `BookingEvidencePanel` queries the shared record for `accepted`, `completed`, `review_window`, and `closed` member-wallet bookings; the presentation keeps both rows visible after completion with loading and closed-window states, while upload/skip stay gated on the accepted state. No images, storage IDs, or upload metadata leave the query.
3. Completion errors. `completionErrorMessage` is a finite allowlist mapping the nine recognized `markCompleted` Convex messages to fixed product copy; unrecognized or redacted errors fall back to generic copy. Raw server strings are never rendered.
4. Submitted reviews. Protected `app/review/[id].tsx` uses `reviews.viewerSubmission` (private to the reviewer) with loading, signed-out, and not-available states, reusing like/save, member-profile navigation, comment create/delete, and the native full-screen image viewer. Public Companion reviews keep feed/link sharing. Private Companion-to-member reviews use `revieweeDisplayName` and expose no public sharing control. `BookingSafetyActions` captures the `submit` return id and both booking detail screens link `viewerReviewId` to "View your review". Web `/review?reviewId=` links normalize to `/review/<id>`. No review editing exists in backend or web, so none was invented. The review dialog includes a native live-card preview (`ReviewContent` with draft stars, note, and photo) plus the honest feed note.
5. Nearby. The screen defaults to consented saved coordinates with no GPS prompt. Explicit device location calls `users.updateApproximateLocation` only when the member is ready and consented, then uses the returned jittered point. Denied permission preserves the existing search with a permission message. Without saved-location consent, an explicitly obtained fix is used only as a transient rounded search origin. Save failure is reported while the transient search continues. Onboarding retains the raw fix only long enough to send it for backend jitter and shows a separately rounded preview. Account-scoped request generations prevent location and geocode results from updating a later member's screen.
6. Withdrawals. Wallet and profile expose "Withdraw funds" for verified members. `companion-finance` works when `finance.dashboard` is null by rendering real `memberDashboard` + `withdrawals.dashboard` balances (no fabricated zeros), hides Companion-only sections, and preserves read-only history with disabled payout actions plus a verification notice when `identityEligible` is false.
7. Circle drafts. Member-scoped persistence uses `SecureStore` on native and local storage on web with legal platform keys. A serialized generation controller ignores hydration after typing or account changes and orders writes before discard/success removal. Discard failure stays visible; a post-create removal failure gets an explicit native alert.
8. Verification and composer. Home composer shows the viewer avatar with "Posting as" copy. The signed-in profile avatar carries the self-accent verified badge with the "Identity and Companion profile verified" explanation when identity is approved and a non-draft Companion profile exists, matching web badge semantics. Companion conversation cards are role-aware: requesters see "Booking total ... Includes service fee", Companions see "Your entitlement ... The member paid ...".

## Empty-booking calendar follow-up

The Bookings tab already defaults to Calendar for both empty and populated accounts. The follow-up preserves that default and keeps the current month, today selection, full day grid, and month navigation visible when both booking lists are empty. The message below the calendar now reads "No bookings yet" and "Future bookings appear here." instead of asking members to select a marked date that does not exist. Header wrapping supports 320-pixel screens, and outside-month dates use the existing muted text token without an opacity reduction that failed contrast checks.

Regression coverage exercises empty grouping, current-month/today initialization, empty-calendar rendering, month and date selection, populated-day guidance, narrow layout, and dark mode. Root checks passed: `pnpm typecheck`, `pnpm test` (1,890 tests, including 495 mobile), `pnpm build`, and `pnpm validate:ui` (310 web/admin and 309 mobile browser tests). Browser inspection confirmed no horizontal overflow in the 320-pixel empty-calendar story. Installed-device behavior remains unverified.

## Centralized legal documents follow-up

The Terms and Conditions and Privacy Policy now come from one shared catalog (`termsDocument`, `privacyDocument`, and `policyDocuments` in `packages/shared/src/policy.ts`) rather than repeated titles, paths, and acceptance labels per surface. Both web and mobile generate acceptance controls, document links, page headings, section order, crosslinks, version, and effective date from that catalog.

Legal access now survives onboarding. Web Settings has a Legal and privacy section, signed-out web visitors have Terms and Privacy footer links, and the mobile Profile settings groups link to both documents. Mobile routes `/terms-and-conditions` and `/privacy-policy` render one shared `PolicyDocumentScreen` with the same crosslinks as the web pages. Both routes stay public and exempt from onboarding redirects.

Tests cover the shared catalog, web policy links, settings legal entries, and the mobile presentation and route wiring. This follow-up intentionally edits shared and web files in addition to mobile, superseding the mobile-only note above for these policy surfaces.

Root checks passed after the follow-up: `pnpm typecheck`, `pnpm test` (1,896 tests, including 498 mobile), `pnpm build`, and `pnpm validate:ui` (310 web/admin and 310 mobile browser tests). Installed-device behavior for the new profile links remains unverified.
